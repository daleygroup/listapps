## Notes
- Stack is fixed by docs/02: Next.js 16, TypeScript, Supabase (Postgres, Auth, Storage), Drizzle, Vercel, Satori + resvg-js, pdf-lib. Rendering workers on a container host later (docs/04).
- Migrations are hand-written numbered up/down SQL pairs run by `lib/db/migrator.ts` (`pnpm db:migrate`), not drizzle-kit generated, so RLS and reversibility stay readable. Drizzle ORM is still the query layer. Bookkeeping lives in the `listapps_meta` schema so Supabase's API never exposes it.
- DB tests (`pnpm test:db`) spin up a throwaway local Postgres per file; when run as root they drop to the `postgres` user. CI runs them on GitHub's runner. See docs/TESTING.md.
- `next.config.ts` has `cacheComponents` on (Next 16 default template). Anything reading the clock or the session must be dynamic; the fixture shell uses a fixed clock for now.
- Implementation notes from M1-4: ancestor `accounts` rows are readable in full (RLS is row-level; the row holds only name, contact, timezone, and policy fields). Sales and sales_admin are both excluded from audit history and agent profiles. App SQL must schema-qualify ltree operators (`operator(extensions.@>)`), as Supabase keeps ltree in the `extensions` schema. Seat counts and plan details are visible to every member who can see a subscription row; restricting them to owners is a service-layer job when the billing screens exist.
- Open technical items for the M1-4 build: how seat holders are recorded (the resolver accepts a `holdsSeat` callback; proposal 001 only has a `seats_used` counter), and whether `past_due` keeps access during a grace period (a business call, only matters once billing exists).
- The shell header is decided per request inside a Suspense boundary (`components/shell/shell-layout.tsx`), so a build without sign-in settings never bakes sample data into a deployment. Seat holders are still not recorded, so a subscription with a seat limit that is full shows as read-only to everyone, holders included; fine for the demo (no seat limits), fix with the billing screens.
- App placeholder pages are reachable by URL whether or not the user is entitled; route guarding arrives with authentication (M1-5).
- Impersonation services write their audit rows with server privileges inside the same transaction as the RLS-checked change (`set local role authenticated`, then `reset role`), so an action and its log row always land together. One live session per staff member at a time, 5 to 240 minutes (default 60). The notice email wording is not written yet; it is customer-facing, so it will go to Joseph as a decision alongside D-005.
- Auth: with no Supabase variables the proxy passes everything through and the auth pages say sign-in is not set up, so builds and CI need no secrets. The app refuses to start if a service role key has a `NEXT_PUBLIC_` name, or if the URL looks like production without an explicit override. Post-sign-in redirects accept same-site paths only. Recommended Supabase setting: public sign-ups off (invitation only), see docs/AUTH-SETUP.md.
- Invitations: only a SHA-256 hash of the link token is stored; the raw token is returned once to the caller that sends the email. Links last 7 days by default (1 hour to 30 days allowed), are single-use, and resending replaces the old link. Accepting is the only server-privileged step and records the person as the audit actor. Invitation events are written right after the RLS-checked change commits (same two-step pattern as offboarding).
- Invite accept page: the contact policy box shows the account's policy text verbatim plus the fixed promise "every contact you own stays yours if you ever leave". The policy values themselves are D-007. New-person sign-ins are created with the server-only `SUPABASE_SERVICE_ROLE_KEY` (see docs/AUTH-SETUP.md); the app's own database connection (`lib/db/server.ts`) uses `DATABASE_URL` and refuses production.
- The clickable demo prototype for October 30 is built and published outside this repo. Do not build prototype screens here.
